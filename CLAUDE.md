# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Telegram Mafia (mafiya) game bot — grammY + Prisma + PostgreSQL + TypeScript. Long-polling, no HTTP server.
All user-facing text, code comments, and test names are in **Uzbek**. Match that when editing.

`PRD.md` is the game-design spec (role list, night order, visit model). It is the authority for game rules;
read it before changing role mechanics.

## Commands

```bash
npm run dev            # tsx watch src/index.ts (needs .env with BOT_TOKEN + DATABASE_URL)
npm run build          # tsc -> dist/
npm test               # tsx tests/run.ts — all scenarios, writes tests/report.md
npx tsc --noEmit       # typecheck only (fast; run this after every edit)
npm run db:generate    # prisma generate
npm run db:push        # prisma db push (schema -> DB, no migration file)
npm run db:studio      # prisma studio
docker compose up -d   # bot + postgres
```

`npm test` **exits 1** — there is a standing set of pre-existing failures (Hujjat, Komissar
otish rejimi, Aktiv rol pool). Compare pass counts before/after your change rather than
expecting a green run. `tests/report.md` is generated by the run and is tracked in git.

### Running a subset of tests

`tests/run.ts` has no filter flag. To run specific scenarios, write a throwaway file in `tests/`
that imports the harness directly, run it with `npx tsx`, then delete it:

```ts
import { runScenario, Scenario } from "./harness";
const cases: Scenario[] = [{ name: "...", players: [...], roles: {...}, nights: [...], afterNight: [...] }];
(async () => { for (const c of cases) console.log(await runScenario(c)); })();
```

The `*.smoke.ts` files in `tests/` are run manually (`npx tsx tests/<name>.smoke.ts`);
`text-service` and `role-templates` need a live DB, `role-repeat` does not.

## Architecture

### Layering

```
handlers/ (grammY Composers)  →  GameController  →  GameEngine  →  repositories/  →  Prisma
                                       ↓
                              NotificationService (all Telegram sends)
```

- **`game/engine.ts`** (~1900 lines) — all game rules. No Telegram. Returns `NightResult`
  (`killed` / `saved` / `events[]`); the caller renders events. Repo calls inside are
  fire-and-forget `.catch(log)` so rule logic stays synchronous.
- **`game/controller.ts`** — phase lifecycle (registration → night → day → voting → confirm),
  timers, and everything that talks to Telegram via `NotificationService`.
- **`game/manager.ts`** — in-memory registry of live engines keyed by `chatTelegramId`.
  Also the **only** place players join a game (`addPlayerToGame`), so it is where per-game
  inventory is reserved.
- **`game/phases/*`** — per-phase prompt/story senders, called by the controller.

### Persistence & restart

The whole engine is serialized to `Game.state` (JSON) — see `game/persistence.ts`. `persistSoon()`
debounces writes at 500 ms. On boot, `index.ts::restoreActiveGames()` rebuilds engines, re-arms the
phase timer from `pendingPhaseAction` + `timerEndsAt`, and cancels any game still in `WAITING`.

**Any new `PlayerState` field must be added to `SerializedPlayer` + both (de)serializers**, or it
silently resets on bot restart. Use `?? fallback` when deserializing so old snapshots still load.

### Night resolution — read before touching

`processNightActions()` is one long numbered sequence (1. Kezuvchi … 19. Professor). It accumulates:

- `killTargets: Map<targetId, DeathCause>` — **a Map, so a later step overwrites an earlier
  cause for the same target, and two simultaneous attacks collapse into one entry.**
- `killActors: Map<targetId, actorId>` — who killed whom. Always write kills through the local
  `setKill(target, cause, actor)` helper so this stays in sync.
- `healedTargets: Set` — doctor
- `sniperTargets: Set` — the SNIPER role bypasses all protection (leaves the shield intact)
- `bulletTargets: Set` — the "Snayper o'qi" item bypasses all protection **and destroys the shield**

Protection checks must key off the **sets**, never off `cause !== "SNIPER_KILL"` — a later killer
can overwrite the cause and defeat the bypass. Step order is load-bearing; moving a role changes
who sees whose visit (`visitorsMap`) and who overwrites whose kill.

`killActors` also drives the Kamikaze night explosion: whoever actually kills a KAMIKAZE dies with
them, unstoppably, resolved after the main kill loop. For the collective mafia kill the "actor" is
resolved by `resolveMafiaKiller()` (the Don who voted for that target, else the first live voter).

### Inventory economy — reserve then finalize

Paid items (Shield / Hujjat / Snayper o'qi) are **not** deducted at purchase or at join:

1. `inventoryService.consumeForGame()` at join (`manager.ts`) reads the `use*NextGame` flags and
   sets `hasShieldActive` / `reservedShield` on `PlayerState`. Active role *is* consumed here.
2. `inventoryService.finalizeForGame()` at `controller.endGame()` compares `reservedX` vs the
   in-game flag to decide whether the item was really used, and only then decrements.

Consequences: a cancelled game (`/stopgame`, too few players) never finalizes, so nothing is lost;
and enabling a toggle *after* joining has no effect on the current game.

### Text and pricing are DB-overridable

- `services/text-defaults.ts` holds every string keyed by dotted name. `textService.preloadAll()`
  at boot loads admin overrides from the `Config` table (`text_` prefix) into a sync cache, so
  `t("key", { params })` is synchronous. **Never hardcode user-facing strings** — add a key to
  `text-defaults.ts`. A missing key returns the key itself, which is how callers detect "no story".
- `services/pricing.service.ts` uses the same `Config` table for `PRICE_KEYS` + per-role prices,
  each with a currency (`diamond` | `money`). Prices are owner-editable at runtime (`/setprice`,
  `/admin`), so never assume a literal price.

### Tests

`tests/harness.ts` **overwrites every method on `gameRepo`/`playerRepo` with no-ops before
importing the engine** — that import order is why the engine can be exercised with no DB.
Scenarios are declarative (`players`, `roles`, `inventory`, `nights[]`, `votes[]`, `afterNight[]`).
`tests/run.ts` buckets results into categories by keyword-matching the scenario **name**
(see `categorize()`), so name new scenarios with the role word in them.

The harness builds `PlayerState` by hand and does not exercise `consumeForGame`/`finalizeForGame` —
the inventory/economy layer has no scenario coverage. Verify that layer by stubbing
`(prisma as any).user` in a throwaway script.

## Gotchas

- `DON` and `MAFIA` collapse into a single night slot in `pendingNightRoles`.
- Docker runs `prisma db push` on start, not `migrate deploy` — `prisma/migrations/` is incomplete.
  Schema changes reach prod via push; destructive changes fail the container rather than drop data.
- `index.ts` swallows `unhandledRejection` / `uncaughtException` on purpose (one broken game must
  not kill every other game), so a thrown error in a phase callback shows up only in logs.
- Owner-only commands live in `handlers/commands/owner.ts` (~1300 lines) and are gated by
  `OWNER_IDS` from env via the `ownerOnly` guard.
- `ctx.dbUser` is populated by `handlers/middleware/auth.ts`; banned users are dropped silently there.
